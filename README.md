# kolibri-core

Переносимое ядро бинарного протокола Komet на C.

C89 плюс `<stdint.h>`, ноль зависимостей, ноль аллокаций. Ни сокетов, ни
потоков, ни файлов, ни глобального состояния: на входе байты, на выходе байты,
все буферы даёт вызывающая сторона. Один и тот же файл собирается clang 3.x под
armv7 и MSVC 2013 под Windows Phone 8.1 — и тем же clang 20 под arm64 сегодня.

Эталон — Rust-реализация [`kolibri-net`](https://github.com/KometTeam/kolibri).
Она остаётся мерой правды: вектора для тестов снимаются с неё, и оба
направления сверяются побайтно.

## Что уже есть

| | |
|---|---|
| Кодек пакета | 10-байтный заголовок big-endian, сборка и разбор |
| Реассемблер | поток из сокета обратно в пакеты, на буфере вызывающей стороны |
| LZ4 block | распаковка и упаковка, без внешних библиотек |
| Сжатие | флаг разбирается на три случая: без сжатия, zstd, LZ4 block |
| zstd | распаковка подключаемым бэкендом; адаптер к libzstd в комплекте |
| MessagePack | чтение курсором и запись в буфер, без аллокаций и без рекурсии |
| Машина сессии | handshake, мультиплекс по seq, keepalive, таймауты, backoff |
| Прокси | HTTP CONNECT и SOCKS5, обе схемы с авторизацией — тоже sans-IO |
| Транспорт | TCP, DNS, неблокирующий connect, подключение TLS-бэкенда |
| TLS | два бэкенда за одним интерфейсом: OpenSSL и mbedTLS |
| Авторизация | anti-spoof fingerprint, 3×SHA-256 своей реализацией |
| Структуры опкодов | 168 опкодов и типы запросов генерируются из `schema/` |
| Медиа | HTTP-запрос и разбор ответа, заголовки трёх режимов, докачка кусками |
| JSON | ридер без аллокаций поверх буфера вызывающего |
| WebSocket | сборка и разбор кадров RFC 6455, маскирование клиента |
| Звонки | разбор vcp, событий ws2 и sans-IO сигнализация сигналинга |
| msgpack↔JSON | мост в обе стороны: логи и отправка пейлоадов через JSON |
| Тап на трафик | колбэк на каждый пакет в обе стороны с распакованным msgpack |

Payload `sessionInit` и `ping` совпадают с эталонными байт в байт. Запросы
на загрузку медиа — тоже, вплоть до порядка заголовков.

Anti-spoof fingerprint (`mode`) проверен на живом сервере: код по SMS доходит.

Чего пока **нет**: упаковки LZ4 frame — она официальным клиентом не
используется, проверено по байткоду 26.28.

## Сборка

```
make            # статическая и разделяемая библиотеки в build/
make test       # 145 тысяч проверок, включая вектора эталона и битый вход
make asan       # тот же прогон под ASan и UBSan
make c89        # строгий C89 с -pedantic-errors: тот диалект, что примет MSVC 2013
make shared     # только разделяемая библиотека, для ctypes
make python-test
make client     # полный клиент на C; с TLS: make client OPENSSL=<префикс>
make zstd-check ZSTD=/usr/local     # адаптер к libzstd на настоящих данных
make integration            # прогон против сервера на localhost
make integration OPENSSL=/usr/local/opt/openssl@3   # плюс сценарий с TLS
```

`make integration` поднимает на localhost сервер, говорящий на протоколе, и
фальшивые прокси — в том числе враждебные, — после чего гоняет собранный клиент
по десяти сценариям: напрямую, через HTTP CONNECT и SOCKS5 с авторизацией и без,
через прокси с конвейером ответов, поверх TLS со своим корнем; и отдельно
проверяет, что недоверенный сертификат отвергается, что хвост от прокси без TLS
доходит, а под TLS считается подделкой.

Туда же входит `make socket-checks` — то, для чего нужен настоящий обрыв
соединения: запись в сброшенный сокет обязана вернуть ошибку, а не убить
процесс-хозяин сигналом.

Тестам и генератору векторов нужен только Python 3 из коробки. Rust нужен
единственный раз — чтобы пересобрать вектора, и результат лежит в репозитории
готовым.

## Устройство API

Всё построено на одном правиле: **ядро никогда не выделяет память и никогда не
удерживает чужие указатели**. Буфер отдали, функция записала, вернулась.

```c
uint8_t packet[4096];
size_t  packet_len;

kb_encode(KB_CMD_REQUEST, /* opcode */ 64, /* seq */ 1,
          msgpack, msgpack_len, packet, sizeof packet, &packet_len);
```

Разбор входящего потока:

```c
uint8_t buffer[64 * 1024];
kb_rx   rx;
kb_rx_init(&rx, buffer, sizeof buffer);

kb_rx_push(&rx, chunk, chunk_len);

const uint8_t *raw;
size_t raw_len;
while ((raw = kb_rx_next(&rx, &raw_len)) != NULL) {
    kb_header header;
    uint8_t   body[64 * 1024];
    size_t    body_len;
    if (kb_decode(raw, raw_len, &header, body, sizeof body, &body_len) == KB_OK) {
        /* body — распакованный MessagePack */
    }
}
```

Из этого правила следует всё остальное: из ctypes такое вызывается без обёрток
на C и без освобождения памяти, в cgo можно передавать `unsafe.Pointer` на
память Go, а двойной free через границу языков просто невыразим.

## Машина сессии

Тоже sans-IO. Сессия не открывает сокетов, не спит и не смотрит на часы — она
только считает, что и когда должно произойти:

```c
kb_session_on_connected(&s, now);      /* TCP и TLS готовы */
for (;;) {
    kb_session_tick(&s, now);          /* время идёт */

    while ((out = kb_session_pull_out(&s, &n)) != NULL) {
        send(fd, out, n);
        kb_session_consume_out(&s, n);
    }

    n = recv(fd, buf, sizeof buf);
    kb_session_feed(&s, buf, n);

    while (kb_session_poll_event(&s, &event) == KB_OK &&
           event.type != KB_EVENT_NONE) {
        /* STATE, HANDSHAKE, RESPONSE, PUSH, REQUEST_FAILED, ERROR */
    }

    wait_until(kb_session_next_deadline(&s));
}
```

Что она берёт на себя: собирает и ставит в очередь `sessionInit` при
подключении, разбирает ответ и достаёт `callsSeed`, нумерует seq (предынкремент
с переносом, первый запрос получает 1), различает ответ и пуш по команде, а не
по совпадению seq, шлёт keepalive через интервал после подключения, следит за
таймаутами запросов и считает лестницу переподключения — 2, 4, 8, 15, 15 секунд,
как в эталоне.

Памяти по-прежнему не выделяет: буферы приёма, отправки, распаковки и таблицу
ожидающих запросов даёт вызывающая сторона.

## Транспорт

Единственная часть проекта, которая знает про операционную систему, — и она
**необязательная**. Хост со своим сокетом (Python, Go, Flutter) её не
подключает: он просто кормит машину сессии байтами. Транспорт нужен там, где
клиент целиком на C — на старых iOS и Windows Phone.

```c
kb_transport_config config;
config.host = "api.oneme.ru";
config.port = 443;
config.connect_timeout_ms = 10000;
config.proxy = &proxy;   /* NULL — напрямую */
config.tls = &tls;       /* NULL — обычный TCP */

kb_transport_connect(&transport, &config);
while (kb_transport_handshake(&transport, &want_write) == KB_ERR_TRUNCATED) {
    kb_transport_wait(&transport, want_write, 10000);
}
```

Полный клиент — `examples/c/client.c`: транспорт, прокси, TLS и машина сессии
вместе, сотня строк цикла.

### Прокси

HTTP CONNECT и SOCKS5 (RFC 1928 и 1929), обе схемы с логином и паролем.
Написаны как машины состояний без ввода-вывода: транспорт их прокручивает, а
тесты гоняют оба протокола целиком, включая отказы и разбор ответов, без
единого сетевого вызова.

Байты, пришедшие вместе с ответом прокси, не теряются: рукопожатие сообщает,
сколько из них съело, а остаток транспорт отдаёт как первые байты туннеля.

### TLS

Ядро не знает ни про один криптостек. TLS подключается таблицей из четырёх
функций:

```c
typedef struct {
    int  (*handshake)(void *ctx);
    long (*read)(void *ctx, uint8_t *buf, size_t len);
    long (*write)(void *ctx, const uint8_t *buf, size_t len);
    void (*close)(void *ctx);
    const char *(*detail)(void *ctx);
} kb_tls_vtable;
```

В комплекте бэкенд на OpenSSL (`src/kolibri_tls_openssl.c`, собирается при
`KB_WITH_OPENSSL`) — он же образец: под mbedTLS, wolfSSL, Secure Transport или
SChannel файл пишется по тому же шаблону и того же размера.

Для старых платформ нужен именно **mbedTLS** — системного TLS 1.2 там нет. Его
адаптера в репозитории пока нет намеренно: писать код, который негде собрать и
прогнать, значит выдавать непроверенное за готовое. Интерфейс под него готов, и
это следующий шаг.

### Сжатие: флаг решает формат

Старший байт `packedLen` — не «сжато/нет», а **дискриминатор формата**. Так его
трактует официальный клиент (класс `zfb` в 26.28):

| флаг | тело |
|---|---|
| `0x00` | как есть |
| `0xFF` | **zstd** |
| прочее | **LZ4 block**, а само значение — оценка степени сжатия |

Исходящее сжимается только LZ4 block: zstd-компрессора у клиента нет вовсе, его
`libzstd.so` экспортирует единственную функцию распаковки. Поэтому в ядре zstd
тоже только на распаковку, и подключается он снаружи — как TLS:

```c
kb_zstd_enable();   /* при сборке с KB_WITH_ZSTD */
```

Без этого тело с флагом `0xFF` даст `KB_ERR_UNSUPPORTED` — понятную ошибку, а не
мусор. Свой распаковщик ставится через `kb_set_zstd_decompressor`.

LZ4 frame протоколом **не используется**: в клиенте frame-классы лежат в
библиотеке, но не вызываются ни разу, и сниффинга магии там нет. В ядро он не
добавлен намеренно.

Исходящий флаг зажат в `0x01..0xFE`. Формула `(ratio + 1)` даёт `0xFF` при
степени сжатия 254 — на мегабайте нулей это воспроизводится, — и сервер принял
бы наш LZ4-блок за zstd-кадр.

### Граница доверия

Прокси недоверенный по определению — иначе он не был бы посредником. Отсюда
правило: **под TLS байты, пришедшие до рукопожатия, не могут быть данными
приложения.** Клиент ещё не отправил ClientHello, значит всё, что прокси
дописал за своим ответом, сочинил он сам. Такое соединение отвергается
(`kb_transport_set_tls` вернёт `KB_ERR_STATE`).

Без TLS тот же хвост — законные данные туннеля, и он доходит до приложения
полностью.

Это не теория: состязательный аудит пробил ровно здесь. Прокси отвечал
`200 Connection established` и приклеивал к ответу поддельный кадр PUSH, после
чего честно проксировал к настоящему серверу. Клиент печатал `tls=ok` —
сертификат проверен по своему корню — и отдавал приложению кадр, которого
сервер не отправлял. Оба исхода закреплены тестами в `make integration`.

Проверка сертификата — забота бэкенда и хоста. Для `api2.oneme.ru` в него
передаётся корень Минцифры; в интеграционном тесте ровно так же передаётся свой
самоподписанный корень, и клиент обязан отвергнуть сертификат, которому не
доверяет.

## Python

```python
import kolibri_core as kb

packet = kb.encode(opcode=64, seq=1, payload=msgpack_bytes)
sock.sendall(packet)

rx = kb.Receiver()
rx.push(sock.recv(65536))
for raw in rx:
    header, payload = kb.decode(raw)
```

Целиком, с машиной сессии:

```python
s = kb.Session(device_id="...", user_agent=kb.UserAgent())
s.on_connected(now_ms())
sock.sendall(s.take_outgoing())
s.feed(sock.recv(65536))
for event in s.events():
    ...   # handshake, response, push, request_failed
```

Ядро sans-IO, поэтому сокет и TLS остаются питоновскими — обычные `socket` и
`ssl`. Тот же расклад, что у `h11` и `h2`, только разбор написан на C.

### Пейлоады не пишутся руками

Для скриптов есть `kb.Connection` — блокирующий клиент (TLS + сессия + цикл
запрос-ответ) с **методом на каждую операцию**, сгенерированным из
`schema/*.toml`. Имена полей сверяются со схемой, опкод подставляется сам,
`bytes` уходят как `{"$bin": …}`, а ответ приходит объектом с атрибутами:

```python
with kb.Connection("api.oneme.ru", device_id="...", user_agent=ua) as c:
    seed = c.handshake()
    mode = kb.fingerprint(seed, device_id, signature, so, dex)

    r = c.auth_request(phone="+7...", type="START_AUTH", mode=mode)  # 17
    r = c.auth_verify(token=r.token, verifyCode=code, authTokenType="CHECK_CODE")
    r = c.login(token=login_token, interactive=True, chatsSync=-1)    # 19
    print(r.profile, len(r.chats or []))
```

Опечатка в имени поля или пропуск обязательного — сразу `TypeError`. Под капотом
всё те же `kb.to_msgpack`/`kb.to_json` (мост msgpack↔JSON) — они доступны и
напрямую, если нужен произвольный пейлоад.

`examples/python/login.py` — полный вход этим API (код по SMS и 2FA), ~25 строк
логики. `examples/python/client_loop.py` — низкоуровневый цикл на голой сессии,
если нужен полный контроль.

Тесты гоняют цикл сессии через `socket.socketpair()`, а типизированный слой —
на заглушке, так что сквозной путь проверен без выхода в сеть.

## Дифференциальная проверка

Порт совпадает с эталоном или не совпадает — это проверяется, а не
предполагается, и в обе стороны.

**Rust произвёл, C разобрал.** `tests/vectors.json` снят с `kolibri-net`
отдельным дампером: 24 случая кодирования байт в байт, 198 разбора пакетов
(включая сжатые тела, которые произвёл `lz4_flex`), 53 LZ4-блока, 5 битых
потоков с ожидаемыми кодами ошибок, 7 раскладок потока по кускам, 48 скаляров
MessagePack на всех границах ширины представления и 3 целых документа
(handshake, ping).
`tools/gen_vectors.py` превращает JSON в таблицы на C, так что тестам не нужен
парсер JSON. Прогоняется каждым `make test`.

**C произвёл, Rust разобрал.** `make dump` печатает то, что собрало C-ядро;
верификатор на Rust читает этот дамп и проверяет эталоном. Нужен, когда
меняется компрессор: свои сжатые блоки обязан понимать не только свой
распаковщик.

Пересобрать вектора (нужен Rust и `kolibri-net`):

```
cargo run --release --manifest-path ../oracle/Cargo.toml > tests/vectors.json
make vectors
```

Дампер оракула и верификатор живут рядом с `kolibri-net`, а не здесь: в этом
репозитории нет ни строчки Rust.

## Битый вход

Ядро разбирает недоверенные байты из сети, поэтому отдельный проход портит
корректные данные и скармливает их обратно: случайные правки, обрезка хвоста,
полностью случайные блоки, мусор в реассемблере. Вокруг выходного буфера
разложены канарейки, так что запись за границу видна даже без санитайзеров, а
`make asan` ловит то, что канарейки пропустят.

Это не формальность. Ручная арифметика смещений в LZ4-распаковщике — ровно то
место, где C стоит дороже всего, и цену за него платят фаззингом.

## Потолок распаковки

`KB_MAX_DECOMPRESSED_SIZE` (32 МБ) применяется к **накопленному** выходу, а не
к отдельному полю длины: превышение даёт `KB_ERR_LIMIT` независимо от того,
насколько велик буфер вызывающей стороны. Это отдельный код, а не
`KB_ERR_TOO_LARGE`, именно чтобы циклы «попробуй с буфером побольше» в
обёртках понимали, что повтор бесполезен.

Так было не сразу: первая версия проверяла потолок лишь на одном поле длины, и
блок в 1,25 МБ разворачивался в 320 МБ со статусом «ок». Нашёл состязательный
аудит, воспроизвёл скептик, регрессия закрыта тестом
«потолок распаковки не зависит от размера буфера».

## Схема протокола

`schema/*.toml` — единственный источник правды о протоколе, и из неё
генерируется код:

| | |
|---|---|
| `schema/opcodes.toml` | 179 опкодов → `kolibri_opcodes.h/.c` плюс поиск имени |
| `schema/*.toml` (ops) | 77 операций + 24 типа: структуры, кодировщики и разборщики → `kolibri_ops.h/.c` |

```sh
make opcodes    # таблица опкодов
make schema     # структуры операций
```

Сгенерированное коммитится: пользователю ядра генераторы не нужны, а изменения
схемы видно в ревью. CI проверяет, что оно не отстало.

Отображение типов подобрано под sans-IO — **разбор ничего не копирует**:

```c
kb_str  строка   данные и длина, указывают внутрь исходного буфера
kb_bin  бинарник то же самое
kb_raw  массив, map или вложенная структура — сырой кусок msgpack
```

Массивы и вложенные map намеренно не разворачиваются в структуры: без
аллокаций пришлось бы гадать про максимальные размеры. Вместо этого поле
отдаётся куском вместе с количеством элементов, а обходит его курсор из
`kolibri_msgpack.h` — без единого лишнего байта:

```c
kb_decode_auth_verify_response(body, len, &resp);
kb_mp_map_get_raw(resp.token_attrs.data, resp.token_attrs.len, "LOGIN",
                  &attr, &attr_len);
kb_mp_map_get(attr, attr_len, "token", &value);
```

Необязательные поля получают спутник `has_<имя>` и при нуле не отправляются
вовсе — сервер отличает отсутствие ключа от `null`.

### Типы из живого сервера

`schema/types_live.toml` — 17 типов (`Chat`, `Contact`, `Message`, `Attach`,
`Keyboard`, `Button`, `ReactionInfo`, `VideoConversation`, `ErrorEnvelope`, …),
выведенных из **живого захвата** сервера (LOGIN на 50 чатов, история чата и
канала, отправка себе) и **парсеров/сериализаторов клиента**. Это те вложенные
объекты, что из декомпила были известны лишь как `any`: теперь у них настоящие
поля с типами и опциональностью.

`Attach` — дискриминированный союз по `_type` (19 вариантов: PHOTO, VIDEO,
AUDIO, FILE, STICKER, SHARE, CALL, CONTACT, LOCATION, POLL, INLINE_KEYBOARD, …):
53 поля, все кроме `_type` опциональны, у каждого в `doc` — к каким `_type` оно.
`Message` — 14 полей со ссылками на `Attach`, `MessageElement`, `ReactionInfo`,
`MessageLink`.

Генератор эмитит на каждый `[types.X]` структуру и декодер `kb_decode_<x>`, так
что вложенность читается типизированно, а не только курсором.

### Извлечено из декомпила

`schema/decompiled.toml` — 61 структура пейлоада, вытащенная из официального
клиента `ru.oneme.app` 26.28. Метод трассируемый, без догадок: enum `x0c` даёт
карту `опкод → класс-парсер ответа`, база билдеров `m5h` кодирует тип полем-
сеттером (`h`=string, `f`=i64, `c`=i32, `a`=bool, `d`=list, `g`=map, `put`=bytes),
а вложенные объекты остаются сырым куском (`any`) под курсор. Каждое поле выверено
adversarial-проходом: в схему попал только тот ключ, что буквально присутствует в
java. У каждого поля в `doc` — откуда оно (`f(j,"chatsSync")` и т.п.).

Декомпил оказался авторитетнее прежней таблицы: он добавил 11 опкодов, которых у
нас не было (`CALL_HISTORY`, `ORG_INFO`, `BANNERS_GET`, …), и обогатил `LOGIN`
пятью полями синхронизации (`contactsSync`, `callsSync`, `lastLogin`,
`bannersSync`, `configHash`).

## Медиа

Загрузка файла — это обычный HTTP на CDN, но с придирчивым сервером: он смотрит
на точную форму заголовков. Поэтому здесь не общий HTTP-клиент, а сборщик
ровно тех трёх запросов, которые шлёт официальный клиент.

| Режим | Что происходит |
|---|---|
| Файл | один POST, `Content-Range` покрывает весь файл целиком |
| Фото | `multipart/form-data`, граница `----KolibriBoundary<n>` |
| Видео | GET узнаёт смещение докачки, дальше куски POST-ами |

Сети модуль по-прежнему не касается: он собирает байты запроса и разбирает
байты ответа, а как их передать — дело транспорта.

```c
kb_url url;
kb_http_header headers[KB_MEDIA_HEADERS_MAX];
size_t count, head_len;
char storage[KB_MEDIA_STORAGE_MIN];
unsigned char head[1024];

kb_url_parse(upload_url, &url);
kb_media_file_headers(&url, "doc.pdf", file_len, user_agent,
                      headers, &count, storage, sizeof storage);
kb_http_build_head("POST", url.path, headers, count, head, sizeof head, &head_len);
/* дальше: отправить head, затем тело файла */
```

Ответ собирается машиной, которую кормят тем, что пришло из сокета, — сколько
бы байт ни принёс каждый `read`:

```c
kb_http_response resp;
kb_http_response_init(&resp, buffer, sizeof buffer);
while (!kb_http_response_done(&resp)) {
    ssize_t n = recv(fd, chunk, sizeof chunk, 0);
    if (n <= 0) { kb_http_response_finish(&resp); break; }
    kb_http_response_feed(&resp, chunk, (size_t)n);
}
int status = kb_http_response_status(&resp);
```

Машина знает три способа, которыми ответ может закончиться: `Content-Length`,
`chunked` и закрытие соединения. Оборванный ответ не выдаётся за целый —
`kb_http_response_finish` вернёт `KB_ERR_TRUNCATED`, а тело останется
недоступным.

Видео режется на куски планом. Он ничего не знает про потоки: раздаёт
диапазоны по одному, поэтому годится и для одного качальщика, и для
нескольких, если вызывающий прикроет план замком.

```c
kb_media_plan plan;
uint64_t from, to;

/* тело GET-ответа — десятичное число уже принятых сервером байт */
uint64_t resumed = kb_media_parse_resume(body, body_len, total);
kb_media_plan_init(&plan, total, chunk_size, resumed);

while (kb_media_plan_next(&plan, &from, &to)) {
    /* ...залить data[from..to] с Content-Range... */
    kb_media_plan_ack(&plan, from, to);
}
```

Мусор в теле GET-ответа или число больше файла означают «начинай сначала», а не
ошибку: так же ведёт себя официальный клиент.

## Звонки

Основной сокет только заводит звонок: опкоды 78/166 отдают `vcp` (или готовый
endpoint), пуш 137 сообщает о входящем. Всё живое идёт по отдельному WebSocket
ws2, а медиа WebRTC остаётся в хосте. Ядро здесь, как и везде, sans-IO: разбирает
и собирает JSON, а сокет, TLS и кадры ведёт вызывающий (для кадров есть
`kolibri_ws.h`).

`vcp` — это `<rawLen>:<base64(LZ4-block(JSON))>`; `kb_vcp_decode` распаковывает
его в буфер вызывающего и даёт доступ к полям, TURN/STUN, времени жизни и
сборке URL подключения ws2:

```c
kb_vcp vcp;
uint8_t scratch[8192];
char url[1024];

kb_vcp_decode(vcp_str, len, scratch, sizeof scratch, &vcp);
kb_vcp_ws2_url(&vcp, conversation_id, NULL, url, sizeof url);
/* дальше: WebSocket на url, а кадры — через kolibri_ws.h */
```

Сигнализация — конверт с нумерацией: запрос несёт `sequence`, ответ возвращает
тот же номер, между ними приходят уведомления, а keepalive — текстовый `ping`,
на который отвечают `pong`. Состояние в ядре — только счётчик seq; сопоставление
ответов ведёт вызывающий.

```c
kb_ws2 ws2;
char cmd[1024];
int64_t seq;

kb_ws2_init(&ws2);
kb_ws2_transmit_sdp(&ws2, peer_id, "offer", sdp, cmd, sizeof cmd, NULL, &seq);
/* seq кладёшь в свою карту ожиданий, cmd отправляешь текстовым кадром */
```

Входящие кадры раскладывает `kb_ws2_classify` (ping / ответ / ошибка /
уведомление), а уведомления разбирает `kb_call_event_parse` в типизированное
событие: `connection` (топология, участники, ICE), `transmitted-data`
(SDP-offer/answer или ICE-кандидат), `hungup`, `closed-conversation`,
`topology-changed`.

## Мост msgpack ↔ JSON

Удобство поверх кодека: превратить пейлоад в читаемый JSON для логов и, наоборот,
собрать пейлоад из JSON вместо ручного msgpack. Работает над байтами, без дерева
значений — по одной проходке в каждую сторону, всё в буфер вызывающего.

```c
/* пришедший ответ — в лог */
char text[4096];
kb_mp_to_json(payload, payload_len, 0, text, sizeof text, NULL);

/* отправить произвольный пейлоад, не собирая msgpack руками */
uint8_t mp[4096], scratch[4096];
size_t mp_len;
kb_json_to_mp("{\"phone\":\"+70000000000\",\"type\":\"START_AUTH\"}",
              len, scratch, sizeof scratch, mp, sizeof mp, &mp_len);
kb_session_request(&session, KB_OP_AUTH_REQUEST, mp, mp_len, &seq);
```

msgpack→JSON лоссовый (для чтения): Binary/Ext становятся base64, нестроковые
ключи стягиваются в строки. Обратное направление восстанавливает то, что хост
пометил явно: `{"$bin":…}` → Binary, `{"$ext":tag,"data":…}` → Ext, ключ
`"$int:<n>"` → целочисленный ключ карты (в JSON нестроковых ключей нет). С
`tagged=1` бинарники round-trip’ятся байт в байт.

Это второй способ слать произвольные пейлоады — первый, `kb_mp_writer`,
никуда не делся; мост лишь избавляет от ручной сборки, когда пейлоад удобнее
описать как JSON.

## Тап на трафик

Отладочный хук: `kb_session_set_tap` ставит колбэк, который срабатывает по разу
на каждый пакет в обе стороны — до диспатча, с уже распакованным msgpack. Порт
`transport/wiretap.rs`. Удобно для лога через мост выше:

```c
static void tap(void *user, kb_tap_direction dir, uint8_t cmd, uint16_t opcode,
                uint16_t seq, const uint8_t *payload, size_t len) {
    char line[4096];
    kb_mp_to_json(payload, len, 0, line, sizeof line, NULL);
    printf("%s op=%u seq=%u %s\n", kb_tap_direction_str(dir), opcode, seq, line);
}
kb_session_set_tap(&session, tap, NULL);
```

`dir` — `KB_TAP_OUT` (клиент→сервер) или `KB_TAP_IN` (сервер→клиент); `cmd` —
командный байт (исходящий всегда REQUEST, входящий — OK/NOT_FOUND/ERROR либо
PUSH). Колбэк должен быть дешёвым: он на горячем пути разбора. Передашь NULL —
тап снимется.

## Примеры

`examples/` — один и тот же сценарий на пяти языках: собрать пакеты, прогнать
их через реассемблер кусками по 7 байт, разобрать. Вывод везде байт в байт
одинаковый.

| | Как подключается |
|---|---|
| `examples/c` | напрямую |
| `examples/go` | cgo по заголовку, без промежуточного слоя |
| `examples/swift` | `import CKolibri` через `include/module.modulemap` |
| `examples/dart` | `dart:ffi`; `ffigen.yaml` показывает автогенерацию |
| `examples/python` | ctypes, плюс полноценный клиент с TLS |

Обёртка в каждом языке — идиоматичный слой на несколько десятков строк:
исключения, срезы байт, автоматическое время жизни. Отдельного FFI-шима нет
нигде, потому что заголовок ядра и есть публичный API.

Одна тонкость, общая для всех: `kb_rx` хранит указатель на буфер приёма между
вызовами, поэтому буфер должен жить в нативной памяти, а не принадлежать
сборщику мусора. В примерах это `C.malloc`, `UnsafeMutablePointer.allocate` и
`calloc` соответственно.

## Совместимость бинарей на Windows

Старым компилятором на новую Windows — да, это лёгкое направление: бинарь из
VS2013 работает вплоть до Windows 11, лишь бы рядом был его CRT (или он собран
статически).

Новым компилятором на старую Windows — обычно нет, и ломается это не в нашем
коде. Тулчейн проставляет минимальную версию в заголовке PE, тянет свой CRT и —
главное — записывает в таблицу импорта функции, которых на старой системе нет;
загрузчик отказывает ещё до `main`, даже если эти функции никто не вызывает.

Ровно на это ядро и наступило: `GetTickCount64` требует Vista, а в этой таблице
заявлен XP. Теперь на Windows используется накопитель поверх `GetTickCount`
(есть с Windows 95). Нижнюю границу держит `getaddrinfo` — она с XP.

Отсюда правило: если собираешь **бинарь**, собирай самым старым тулчейном из
нужных. Если раздаёшь **исходники** — а тут именно они, — тулчейн выбирает тот,
кто встраивает, и C89 без зависимостей ему в этом не мешает.
